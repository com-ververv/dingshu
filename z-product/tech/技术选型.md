# Pexar Lark Agent — 技术选型 v0.6

## 1. 结论

本项目基于现有 `desktop-starter-app` Electron 模板改造，不另起炉灶。MVP 技术路线如下：

| 维度 | 选型 | 结论 |
|------|------|------|
| 桌面框架 | Electron 39 + Electron Forge + Vite | 沿用现有工程，避免切换打包体系 |
| 前端 | React 19 + TypeScript + Tailwind CSS 4 + AI Elements / Radix/shadcn 风格组件 | 优先验证 AI Elements + `useChat` + 自定义 IPC transport，失败则降级为本地组件 |
| Agent/LLM | Vercel AI SDK `ToolLoopAgent` / `streamText` + OpenAI Compatible Provider | 直连硅基流动，支持流式、多步工具调用、工具审批和 UIMessage 流 |
| 模型 | `Pro/moonshotai/Kimi-K2.6` | PRD 固定模型，MVP 不做模型切换 |
| 飞书集成 | 内置 `@larksuite/cli` 及其平台二进制，主进程以受控子进程调用 | 不暴露通用 shell，按能力封装工具 |
| 本地存储 | SQLite `better-sqlite3` + Electron `safeStorage` | 会话可查询，凭证不明文落盘 |
| 发布 | Electron Forge makers + GitHub Releases + electron-updater | 沿用模板既有发布能力 |

关键原则：

- 保持现有模板的工程边界：主进程负责 Agent、工具执行、凭证和数据库；渲染进程只负责 UI。
- 优先让 AI SDK `UIMessageChunk` 成为主进程到渲染进程的流式中间格式；若 M1.0 验证失败，再保留自定义 IPC 事件协议。
- 飞书能力不实现通用命令行代理，只实现显式 allowlist 的 `lark-cli` 工具。
- 敏感写操作默认二次确认，包括发消息、创建/改写文档、删除或移动内容；优先使用 AI SDK 工具审批机制落地。
- MVP 不引入 Python runtime、Claude Code Router、独立本地服务或插件系统。

## 2. 和 PRD 的覆盖关系

| PRD 要求 | 技术落点 |
|----------|----------|
| 单窗口、单对话流、流式输出 | React 聊天界面 + 主进程 IPC streaming event |
| 展示工具调用过程，可折叠/展开 | `tool_calls` 表持久化 + 渲染进程按步骤展示 |
| 复制、重新生成 | 消息级操作，重新生成复用同一 conversation 上下文 |
| 停止生成 | 主进程维护 `AbortController`，IPC 暴露 `chat:stop` |
| 文档创建/读取/搜索 | `lark_doc_create` / `lark_doc_read` / `lark_doc_search` 工具 |
| 消息发送/查询 | `lark_message_send` / `lark_message_search` 工具 |
| 会话保存、恢复、删除 | SQLite `conversations` / `messages` / `tool_calls` |
| API Key、appSecret 安全保存 | `safeStorage.encryptString` 后写入本地 `secure_settings` |
| 飞书账号授权入口 | 主进程启动 `lark-cli auth login`，浏览器打开授权 URL |
| 未配置时明确提示 | 启动聊天前做 settings readiness check |
| macOS + Windows 单包安装 | Forge makers 输出 macOS DMG/ZIP、Windows Squirrel installer |
| 无网络时明确提示 | Agent 调用和 lark-cli 调用统一映射网络错误 |

## 3. 现有工程约束

当前仓库不是空白项目，已有可复用基础设施：

- `package.json` 使用 `npm` scripts，核心命令是 `npm run dev`、`npm run make`、`npm run publish`。
- 打包体系是 `electron-forge`，配置入口是 `forge.config.ts`，不是 `electron-builder`。
- 前端已是 React 19、Vite 7、Tailwind CSS 4。
- 数据库已使用 `better-sqlite3`，现有表为 `settings`。
- 自动更新已接入 `electron-updater` + GitHub Releases。
- 应用配置单一来源为 `app.config.ts`。

因此技术方案不迁移到 pnpm/electron-builder/React 18。若未来要迁移包管理器或打包体系，应作为独立技术债处理，不进入 MVP 主线。

## 4. 应用架构

```text
Electron 渲染进程
  React 19 聊天界面
  设置面板
  会话侧边栏
  工具调用过程展示
        |
        | contextBridge 暴露的 window.api
        | IPC request + streaming event
        v
Electron 主进程
  ChatService
    - 会话上下文组装
    - ToolLoopAgent / streamText
    - AbortController 注册表
    - token delta、tool event、error event 分发
  ToolService
    - lark-cli allowlist 工具
    - 敏感操作 confirmation gate
    - stdout/stderr 解析和脱敏
  CredentialService
    - safeStorage 加解密
    - secure_settings 读写
  DatabaseService
    - conversations/messages/tool_calls/settings
  LarkAuthService
    - lark-cli auth login
    - 授权 URL 提取
    - lark-cli profile 目录隔离
        |
        v
内置资源
  @larksuite/cli npm 包和已下载的平台二进制
  SQLite 数据库
  用户级 lark-cli 配置目录
```

进程边界：

- 渲染进程不得直接读取 API Key、appSecret、飞书 token 或执行系统命令。
- 主进程不得把原始凭证、完整 stderr、环境变量回传给渲染进程。
- 所有 IPC 返回统一采用现有 `IPCResponse<T>` 结构；流式聊天额外使用事件通道。

## 5. Agent 与模型

### 5.1 选型

使用 Vercel AI SDK：

- `@ai-sdk/openai-compatible` 创建硅基流动 provider。
- `ai` 包的 `ToolLoopAgent` 作为主要 agent loop。
- 对需要更细粒度 UI 事件的路径，可直接使用 `streamText`，并保留相同工具定义。
- 优先验证 `ToolLoopAgent.stream()` / `streamText().toUIMessageStream()` 产出的 `UIMessageChunk` 能否作为 Electron IPC 的流式中间格式。
- 渲染进程优先实现 `IpcChatTransport`，让 `@ai-sdk/react` 的 `useChat` 消费从主进程转发来的 `ReadableStream<UIMessageChunk>`。
- 使用 `stopWhen: stepCountIs(8)` 作为 MVP 默认上限，避免工具循环失控。
- 写操作工具设置 `needsApproval: true`，让 Agent 在工具执行前产出审批请求；审批通过后再恢复执行。
- M1 spike 后必须在 `ToolLoopAgent.stream()` 和直接 `streamText()` 之间二选一作为正式实现路径；若 `ToolLoopAgent.stream()` 无法满足事件粒度，则统一退到 `streamText()`，避免两套 agent loop 并存。
- M1.0 必须验证 `ToolLoopAgent.stream()` 与 `streamText()` 两条路径下 `needsApproval` 的真实行为；若 `streamText()` 不内置审批拦截，选择 `streamText()` 就意味着主进程需要承担部分自研 tool loop 工作量。

Provider 配置：

```ts
const siliconflow = createOpenAICompatible({
  name: 'siliconflow',
  apiKey,
  baseURL: 'https://api.siliconflow.cn/v1',
  includeUsage: true,
});

const model = siliconflow.chatModel('Pro/moonshotai/Kimi-K2.6');
```

`baseURL` 必须配置为 `https://api.siliconflow.cn/v1`，不能写成完整的 `/chat/completions`；OpenAI-compatible provider 会在内部拼接 Chat Completions endpoint。`apiKey` 正式运行时来自设置面板和 `secure_settings`，通过 `safeStorage` 加密保存；`.env` / 环境变量只允许用于开发调试、CI smoke test 或本地 curl 预检，不作为产品级凭证来源。

`siliconflow.chatModel('Pro/moonshotai/Kimi-K2.6')` 是项目统一写法；若示例或 spike 中使用 `siliconflow('Pro/moonshotai/Kimi-K2.6')`，视为等价写法，但正式代码统一收敛到 `chatModel`，避免 provider 调用风格分散。

模型参数约束：

- `maxOutputTokens` 作为 AI SDK 侧统一输出上限字段；OpenAI Chat Completions 原始 curl 预检中才使用 `max_tokens`。
- `temperature` 默认从 `0.4` 起步；工具调用场景优先使用低温度，减少参数漂移。
- Kimi-K2.6 的工具入参必须继续使用本地 Zod / JSON Schema 校验，不能只信任模型输出。
- 不把 Structured Outputs 作为 MVP 依赖；若 SiliconFlow OpenAI-compatible 链路不支持严格 structured outputs，JSON 格式只作为 prompt / JSON mode 约束，落地前仍由主进程解析和校验。

当前 curl 预检结果：

- `POST https://api.siliconflow.cn/v1/chat/completions` + `model = Pro/moonshotai/Kimi-K2.6` 非流式请求已验证可用，返回 usage 和 `reasoning_content`。
- `stream: true` 已验证能返回 SSE `chat.completion.chunk`；但前段 chunk 会先返回 `delta.reasoning_content`，普通 `delta.content` 可能稍后才出现。M1.0 必须验证 AI SDK OpenAI-compatible provider 是否会忽略、保留或误处理该字段。
- 基础 tool calling 已验证可用，模型能返回 `finish_reason = tool_calls` 和 OpenAI 风格 `tool_calls[].function.arguments`。

当前 AI SDK smoke demo 结果：

- `scripts/siliconflow-ai-sdk-smoke.mjs` 已在独立分支验证 `@ai-sdk/openai-compatible + ai@6 + Kimi-K2.6` 最小链路。
- `generateText` 已验证可返回正文、`finishReason` 和 usage；usage 中包含 `raw.completion_tokens_details.reasoning_tokens`，可用于后续埋点分析。
- `streamText` 已验证可返回可见 text stream；但首个可见 `textDelta` 可能在大量 reasoning tokens 后才出现，实测约 10-13 秒。UI 不能把“未收到 text delta”简单等同于无响应，主进程应尽早发送连接/思考中状态。
- `generateText + tools + stopWhen: stepCountIs(3)` 已验证最小 agent loop：模型发起 tool call -> AI SDK 执行本地 tool -> tool result 回传模型 -> 模型生成最终回答。
- `AI SDK tool -> lark-cli docs +search` 已验证真实只读飞书读取链路：模型调用本地工具，本地工具调用已授权的 `lark-cli` 搜索飞书文档，模型基于搜索结果总结。测试关键词“测试”返回 325 条结果，第一条标题为“软件测试：工作规划”。
- `lark-cli docs +fetch --api-version v2` 已手工验证可读取文档正文；后续正式工具需做 HTML/富文本到模型上下文的清洗和长度裁剪。

已验证能力不等同于完整 MVP agent。`includeUsage`、`reasoning_content` 基础映射、非流式工具调用和只读 lark-cli 子进程调用已通过 smoke；但 streaming tool deltas、`needsApproval`、停止生成、审批恢复、工具失败重试、`ToolLoopAgent.stream()` 事件粒度仍必须由 M1 spike 验证。若这些能力不支持，配置上关闭对应能力，并退回到主进程自实现 tool loop。

### 5.2 失败与降级策略

- Kimi-K2.6 工具调用不稳定时，不在 MVP 内开放模型切换；先通过 prompt、工具 schema、step 上限和工具结果压缩修正。
- 若硅基流动返回限流、鉴权失败或网络错误，聊天流终止并展示可操作错误，不写入失败的 assistant 正文。
- M1 第 1 周必须完成真实链路 spike：`Kimi-K2.6 + ToolLoopAgent + lark_doc_create` 端到端连续 5 次成功，且每次都能正确触发审批、执行工具并返回文档链接。
- 若 spike 失败，兜底路径是：保留 UI 和工具层，主进程改为自实现 JSON tool loop；必要时把“固定模型”作为 PRD 风险回传，而不是在实现末期临时换栈。
- 工具结果按工具类型设置上下文上限：文档读取默认 12,000 字符，消息查询默认先分页再摘要，单页最多 50 条或 16,000 字符。完整原始结果只写本地数据库，不直接塞回模型。

### 5.3 流式、停止和并发

主进程为每条正在生成的 assistant message 创建一个 `AbortController`，以 `conversationId + messageId` 注册。渲染进程调用 `chat:stop(conversationId, messageId)` 后：

1. 主进程触发 `controller.abort()`。
2. 当前 AI SDK stream 和正在执行的 lark-cli 子进程收到 `abortSignal` 后停止。
3. `messages.status` 从 `streaming` 改为 `cancelled`。
4. 所有关联且未完成的 `tool_calls.status` 改为 `cancelled`。
5. UI 收到 `chat:done`，状态为 `cancelled`。

MVP 同一时刻只允许一个活跃生成流。用户在一个会话生成中切到另一个会话时，原流继续展示为“生成中”；再次发送新消息前必须停止或等待当前流结束。取消时已经完成的 step、已确认且已执行的工具调用、abort 时已 flush 的 `parts_json` 都保留；message 行从 `streaming` 改为 `cancelled`。取消后不再追加新的 token delta 或工具结果，被取消的工具调用统一标记 `cancelled`。

### 5.4 流式 IPC 协议

M1.0 优先验证 `UIMessageChunk` 路线：

```text
主进程 ToolLoopAgent.stream() / streamText().toUIMessageStream()
  -> UIMessageChunk
  -> Electron IPC envelope
  -> 渲染进程 IpcChatTransport
  -> ReadableStream<UIMessageChunk>
  -> useChat
  -> AI Elements / 本地 chat components
```

IPC envelope 是应用内部协议，不直接裸传 SDK chunk：

```ts
interface ChatStreamEnvelope {
  protocolVersion: 1;
  streamId: string;
  conversationId: string;
  messageId: string;
  type: 'ui-message-chunk' | 'control' | 'error';
  payload: unknown;
}
```

`protocolVersion` 是 IPC 传输层契约版本；framing、envelope 字段或分发逻辑变化时递增。它与 `parts_schema_version` 独立，不等同于 AI SDK 版本。

如果 `UIMessageChunk + IpcChatTransport + useChat` 的端到端验证失败，则退回自定义 IPC 事件协议。此时流式输出不使用 `ipcMain.handle` 的单次响应，而由主进程通过 `webContents.send` 推送事件。所有事件 payload 都带 `conversationId`、`messageId` 和 `requestId`。

| 事件 | 关键字段 | 数据库行为 |
|------|----------|------------|
| `chat:started` | `assistantMessageId` | 插入 `messages.status = streaming` |
| `chat:delta` | `textDelta`、`partIndex` | UI 增量展示，按节流策略更新 `parts_json` |
| `chat:tool-call-start` | `toolCallId`、`toolName`、`inputPreview` | 插入 `tool_calls.status = running` |
| `chat:tool-call-confirmation-required` | `approvalId`、`toolCallId`、`toolName`、`riskSummary`、`inputPreview` | INSERT 新 `tool_calls` 行，`status = pending_confirmation` |
| `chat:tool-call-result` | `toolCallId`、`status`、`outputPreview`、`elapsedMs`、`errorCode?` | 按事件 `status` 更新 `tool_calls.status`、`finished_at`、`output_json` / `error_message` |
| `chat:error` | `code`、`message`、`recoverable` | 当前 message 标记为 `failed` |
| `chat:done` | `status`、`usage`、`finishReason` | 当前 message 标记为 `completed` / `cancelled` |

确认类事件的响应走 IPC request：

- `chat:approveToolCall(conversationId, messageId, approvalId)`
- `chat:rejectToolCall(conversationId, messageId, approvalId, reason)`

在 `UIMessageChunk` 路线下，审批通道拆成两层：

- 审批发起和状态展示走 custom data part，例如 `data-tool-approval-required`、`data-tool-approval-resolved`。这些 part 进入 `UIMessage.parts`，用于渲染审批卡片。
- 审批响应控制不走 `UIMessageChunk`，仍走独立 IPC handle：`chat:approveToolCall` / `chat:rejectToolCall`，用于 resolve 主进程 pending promise。

M1.0 的 `A1b` 必须验证 custom data part 能从主进程进入 `useChat` 的 `UIMessage.parts`，并能被 AI Elements 或本地 part renderer 渲染。若 custom data part 失败，则审批发起通知退回独立 IPC event，且 `UIMessageChunk` 路线不能作为完整 MVP 路径。

事件语义补充：

- `chat:error` 与 `chat:done` 互斥；error 即终态，UI 收到后立即清理 controller 并关闭流。
- `chat:send` 在事件流开始前先在事务中插入 user message；若 provider 创建失败，user message 仍保留，只发送 `chat:error`。
- `partIndex` 指向 `UIMessage.parts` 数组下标，同一 part 内的 `textDelta` 按出现顺序追加。
- `inputPreview` / `outputPreview` 统一上限 2,000 字符；超出部分仅落库，UI 后续通过详情接口按需读取。
- `chat:error.recoverable = true` 用于网络、限流、超时，UI 展示重试；`false` 用于鉴权失败、未配置、schema 校验失败，UI 引导设置或修正输入。错误码命名空间为 `network.*`、`auth.*`、`tool.*`、`model.*`、`db.*`，与 i18n 文案表一一对应。

状态迁移：

- 非敏感工具：`chat:tool-call-start` -> `chat:tool-call-result(status=completed|failed|cancelled)`。
- 敏感工具批准：`chat:tool-call-confirmation-required` -> `chat:tool-call-start` -> `chat:tool-call-result(status=completed|failed|cancelled)`。
- 敏感工具拒绝或超时：`chat:tool-call-confirmation-required` -> `chat:tool-call-result(status=cancelled)`。
- 同一 `toolCallId` 在 `pending_confirmation` 后进入 `running` 时只能 UPDATE 既有 `tool_calls` 行，不允许 INSERT 新行。
- `chat:tool-call-confirmation-required` 收到已存在的 `toolCallId` 视为状态机违规，主进程拒绝并发送 `chat:error(code = tool.duplicate_approval)`。

审批超时默认 10 分钟，超时等同拒绝，工具调用和当前 assistant message 标记为 `cancelled`。审批等待不计入 `stepCountIs(8)` 的模型调用步数。拒绝时默认把 denied 结果回传给模型，让模型继续生成一段简短的“未执行原因”，不直接伪造成功结果。

ID 作用域：

- `requestId` 对应一次 `chat:send` 或 `chat:regenerate` 调用。
- `messageId` 对应一次 assistant 生成结果。
- `toolCallId` 对应模型发起的一次工具调用。
- `approvalId` 对应一次工具审批请求，作用域限定在同一个 `messageId` 内。

流式落库节流：

- token delta 先在内存中累积。
- 满足任一条件即 flush 一次 `parts_json`：距离上次 flush 超过 200ms、遇到 tool-call 边界、stream end、abort、error。
- flush 时整段 `parts_json` UPSERT，不做 per-token UPDATE。

`IpcChatTransport` 的方法映射：

- `sendMessages` -> `chat:send`
- `stop` / UI stop action -> `chat:stop`
- `regenerate` / `reload` -> `chat:regenerate`
- `reconnectToStream` 默认不做；Electron IPC 同进程生命周期内不依赖 HTTP resumable stream，若后续需要恢复未完成流再单独设计 `chat:reconnect`。

### 5.5 System prompt 版本化

System prompt 由主进程常量和版本号管理，不允许渲染进程动态覆盖。创建会话时写入 `conversations.system_prompt_version`；重新生成时使用会话创建时的 prompt 版本，避免 prompt 迭代后旧会话重放出不一致的工具行为。

### 5.6 重新生成行为

接口定义为 `chat:regenerate(conversationId, assistantMessageId)`。

MVP 采用“保留历史、标记替代”的语义：

1. 找到目标 assistant message 前最近一条 user message 作为重新生成锚点。
2. 目标 assistant message 及其后的 messages 标记 `superseded_at`，关联 tool_calls 标记 `superseded_at`，不物理删除。
3. 使用锚点之前的有效上下文和该会话的 `system_prompt_version` 重新生成新的 assistant message。
4. 会话侧边栏的 `last_message_at`、`last_message_preview` 指向最新未被 superseded 的消息。
5. 复制和恢复会话默认只展示未被 superseded 的消息；调试视图可显示被替代版本。

边界条件：

- 传入已被 `superseded_at` 标记的 messageId 时返回 `INVALID_TARGET`。
- 当前存在 `streaming` message 时返回 `ANOTHER_STREAM_ACTIVE`，UI 必须先 stop 再 regenerate。

## 6. 飞书集成

### 6.1 lark-cli 内置形态决策

MVP 选择 `@larksuite/cli` npm 包作为获取和锁版本方式，但运行时不依赖用户全局 Node 或全局 lark-cli。

落地方式：

- `@larksuite/cli` 加入应用依赖并锁定版本。
- 安装期运行该包的 postinstall，下载对应平台的 `bin/lark-cli` / `bin/lark-cli.exe` 到 `node_modules/@larksuite/cli/bin/`。下载失败必须 fail-fast，不能静默进入“运行期再下载”。
- Forge 打包时把 `node_modules/@larksuite/cli` 中的 `bin/`、`scripts/`、`checksums.txt` 和 `package.json` 复制到 `process.resourcesPath/lark-cli/`。
- 运行期禁止触发网络下载：开发模式直接读 `node_modules` 路径，打包模式读 `process.resourcesPath` 路径。包内 `scripts/run.js` 仅作为开发者本地修复脚本，不由主进程调用。
- MVP 构建采用“目标平台本机 runner 构建目标平台包”的方式，不做单机交叉下载多平台二进制。
- M1 spike 必须确认内置 `lark-cli` 二进制类型（原生编译 / Node SEA / pkg / Bun 等）。若是 V8-based 单体，必须提前验证 macOS hardened runtime 下能启动。

资源路径解析：

```ts
function getBundledLarkCliPath() {
  const exe = process.platform === 'win32' ? 'lark-cli.exe' : 'lark-cli';
  if (app.isPackaged) {
    return path.join(process.resourcesPath, 'lark-cli', 'bin', exe);
  }
  return path.join(app.getAppPath(), 'node_modules', '@larksuite', 'cli', 'bin', exe);
}
```

M1 第 1 周必须验证 dev、`npm run make`、`npm run publish` 产物中的路径解析和执行权限。若发现 npm 包的 postinstall 下载策略不适合打包，再切换为仓库内 vendored 平台二进制资源。

### 6.2 不使用通用 shell tool

初稿里的“让 Agent 执行完整 lark-cli 命令”风险过高，会带来命令注入、越权参数、凭证泄露和不可控副作用。MVP 改为显式工具：

| 工具 | 能力 | 是否二次确认 |
|------|------|--------------|
| `lark_doc_create` | 创建云文档 | 是 |
| `lark_doc_read` | 读取指定文档 | 否 |
| `lark_doc_search` | 搜索云文档 | 否 |
| `lark_message_send` | 发送消息 | 是 |
| `lark_message_search` | 查询消息 | 否 |

后续可扩展日历、联系人、任务等工具，但仍按 allowlist 增加，不开放任意命令执行。

### 6.3 敏感工具审批流程

写操作工具使用 AI SDK `needsApproval` 能力。流程：

```text
模型请求 lark_message_send / lark_doc_create
  -> AI SDK 发现工具 needsApproval
  -> 主进程写 tool_calls.status = pending_confirmation
  -> 主进程发送 chat:tool-call-confirmation-required
  -> 渲染进程展示目标、动作、内容摘要和风险
  -> 用户批准或拒绝
  -> 主进程追加 tool approval response
  -> 批准：继续执行 lark-cli
  -> 拒绝：工具返回 denied，模型继续生成简短的“未执行原因”
```

审批请求必须包含：

- 工具名和自然语言动作说明。
- 目标对象，例如文档标题、chatId、群名或用户。
- 待发送/创建/改写内容摘要。
- 可能的副作用。

拒绝、超时或用户停止生成都必须把对应 `tool_calls.status` 置为 `cancelled`，并让模型上下文得到明确的 denied/cancelled 结果，避免模型误以为操作已经完成。

### 6.4 lark-cli 调用约束

主进程使用 `child_process.spawn(file, args, options)`，禁止 `shell: true`。所有参数由工具 schema 生成，不拼接整条命令字符串。

执行规则：

- `PATH` 不参与解析，使用打包资源中的绝对路径。
- `cwd` 固定到应用数据目录下的 `lark-cli-workdir`。
- `HOME` / `USERPROFILE` / lark-cli 配置目录固定到应用数据目录，避免污染用户全局 lark-cli。
- appId、appSecret 等敏感值通过环境变量传入子进程，不写入命令行参数。
- stdout/stderr 统一按 UTF-8 读取；Windows 如遇编码问题，先设置 `LANG=C.UTF-8`、`PYTHONIOENCODING=utf-8`、`NO_COLOR=1`。
- 子进程超时默认 60 秒；搜索类工具可放宽到 120 秒。
- `spawn` options 必须显式传入 `signal: abortController.signal` 和 `killSignal`；工具执行收到 abort 后返回 `{ cancelled: true }`，不得转成未处理异常。
- Windows 上需验证 lark-cli 是否再派生子进程；若存在子孙进程，停止时使用 `taskkill /T /F` 兜底清理进程树。
- 日志默认只记录命令类型、耗时、退出码和脱敏后的摘要。

### 6.5 授权流程

设置面板提供“授权飞书账号”按钮：

1. 主进程检查 appId/appSecret 是否已配置。
2. 启动 `lark-cli auth login`，优先使用 `--json`、`--print-auth-url` 或等价稳定输出模式。
3. 从结构化输出中提取授权 URL；若当前 lark-cli 版本不支持结构化输出，则固定版本并用 stdout/stderr 正则作为临时兼容层。
4. 用 `shell.openExternal(url)` 打开系统浏览器。
5. 监听 CLI 退出码，成功后写入授权状态。
6. 解析失败时展示可复制的原始授权提示、重试入口和诊断信息，不静默失败。

授权 token 由 lark-cli 写入隔离的应用数据目录；应用自身不解析 token 内容。删除账号授权时，删除该隔离目录并清理授权状态。

M1 spike 必须确认授权进程生命周期：如果 `auth login` 是 long-running 进程，主进程必须把 child process 注册到 abort registry，用户取消授权时 kill 子进程；如果是 short-running 打印 URL 后退出，则补充后续授权状态轮询命令。

`larkAuth:cancel` 与 `larkAuth:logout` 语义区分：前者中止未完成的授权流程并 kill 正在运行的 `auth login` 子进程，状态回到未授权；后者清理已完成授权的账号状态和隔离 profile。

## 7. 凭证与配置

### 7.1 存储策略

| 数据 | 存储位置 | 说明 |
|------|----------|------|
| 硅基流动 API Key | `secure_settings` | `safeStorage` 加密后保存 |
| 飞书 appId | `secure_settings` | appId 可不加密，但为简化读取和删除统一走 secure path |
| 飞书 appSecret | `secure_settings` | 必须加密 |

| lark-cli 授权 token | 应用数据目录下隔离 profile | 由 lark-cli 管理 |

`safeStorage` 不可用时：

- macOS/Windows 正式版本直接阻止保存凭证，并提示系统安全存储不可用。
- 不降级为明文存储。
- 开发环境可通过显式环境变量临时绕过，但不得写入数据库。

### 7.2 IPC API

新增 API 按领域拆分：

- `credentials:set/getStatus/delete`
- `chat:createConversation/listConversations/deleteConversation/send/stop/regenerate`
- `chat:approveToolCall/rejectToolCall`
- `larkAuth:start/cancel/getStatus/logout`
- `settings:get/set/getAll`

渲染进程只能获取凭证“是否已配置”的状态，不获取明文值。

## 8. 数据库设计

现有 `settings` 表保留。新增表使用迁移文件落地，不直接在旧 schema 中改表。建议迁移目录：

```text
src/database/migrations/
  001_create_chat_tables.sql
  002_create_secure_settings.sql
```

迁移机制：

- 自实现轻量迁移 runner，不新增数据库迁移框架依赖。
- 新增 `schema_migrations(version TEXT PRIMARY KEY, applied_at INTEGER NOT NULL)`。
- 启动时按文件名排序读取 `src/database/migrations/*.sql`，在事务内执行未应用迁移。
- 迁移成功后写入 `schema_migrations`；失败则事务回滚、应用启动失败并提示数据库迁移错误。
- 对已有表结构的后续变更必须新增迁移文件，不允许直接修改已发布迁移。
- 初始化数据库连接后执行 `PRAGMA foreign_keys = ON`。当前 schema 未显式声明 `ON DELETE`，按 SQLite 默认 `NO ACTION` 处理；后续物理清理任务必须显式批量删除关联行，不依赖级联。

核心表：

```sql
CREATE TABLE conversations (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  system_prompt_version INTEGER NOT NULL,
  last_message_at INTEGER,
  last_message_preview TEXT,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  deleted_at INTEGER
);

CREATE TABLE messages (
  id TEXT PRIMARY KEY,
  conversation_id TEXT NOT NULL,
  role TEXT NOT NULL CHECK (role IN ('user', 'assistant', 'system', 'tool')),
  parts_schema_version INTEGER NOT NULL,
  parts_json TEXT NOT NULL,
  content_text TEXT,
  status TEXT NOT NULL CHECK (status IN ('streaming', 'completed', 'failed', 'cancelled')),
  superseded_at INTEGER,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  FOREIGN KEY (conversation_id) REFERENCES conversations(id)
);

CREATE TABLE tool_calls (
  id TEXT PRIMARY KEY,
  conversation_id TEXT NOT NULL,
  message_id TEXT,
  tool_name TEXT NOT NULL,
  input_json TEXT NOT NULL,
  output_json TEXT,
  status TEXT NOT NULL CHECK (status IN ('pending_confirmation', 'running', 'completed', 'failed', 'cancelled')),
  approval_id TEXT,
  error_message TEXT,
  superseded_at INTEGER,
  created_at INTEGER NOT NULL,
  started_at INTEGER,
  finished_at INTEGER,
  FOREIGN KEY (conversation_id) REFERENCES conversations(id),
  FOREIGN KEY (message_id) REFERENCES messages(id)
);

CREATE TABLE secure_settings (
  key TEXT PRIMARY KEY,
  encrypted_value BLOB NOT NULL,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
```

索引：

- `messages(conversation_id, created_at)`
- `messages(conversation_id, status)`
- `messages(conversation_id, superseded_at)`
- `tool_calls(conversation_id, started_at)`
- `tool_calls(approval_id)`
- `tool_calls(message_id, superseded_at)`
- `conversations(updated_at)`
- `conversations(last_message_at)`

删除会话采用软删除，避免误删后无法恢复；后续可增加“清空已删除会话”的维护动作。

消息持久化策略：

- `parts_json` 保存 AI SDK `UIMessage.parts` 兼容结构，用于恢复工具调用折叠块、approval 状态和重新生成。
- `parts_schema_version` 是应用内部 schema 版本号，不等同于 AI SDK 版本。只有当 `parts_json` 的解释方式变化时递增，并提供读取时 migrator。
- `content_text` 只保存纯文本预览，供侧边栏、复制和搜索使用。
- 重新生成时由 `parts_json` 转回模型需要的 `ModelMessage`，不从渲染进程拼接上下文。

## 9. UI 选型与页面结构

沿用 React 19 + Tailwind CSS 4。组件优先使用 AI Elements、现有 Radix 依赖和 shadcn/ui 风格封装，不在 MVP 中引入大型全家桶组件库。

AI Elements 使用策略：

- M1.0 优先验证 `AI Elements + @ai-sdk/react useChat + IpcChatTransport`。
- 若 `IpcChatTransport` 路线成立，AI Elements 直接消费 `UIMessage` / `UIMessage.parts`。
- 若 AI Elements 组件在 Vite + Electron + React 19 + Tailwind CSS 4 下存在兼容问题，但 `useChat` 数据通路成立，则只把 AI Elements 当作源码参考，在 `src/renderer/components/chat/` 实现本地 shadcn 风格组件。
- AI Elements / Streamdown 渲染层属于体验项，失败不触发 Agent/IPC 架构回退；真正触发回退的是 `UIMessageChunk -> IpcChatTransport -> useChat` 数据通路失败。

Streamdown 使用策略：

- Streamdown 作为 assistant text part 的流式 Markdown 渲染器，优先替代普通 `react-markdown`。
- 默认禁用 Mermaid 和 KaTeX，除非 PRD 后续明确需要。
- 代码块渲染优先验证 Shiki；若 Electron CSP 或 packaged build 不兼容，则降级到纯 CSS / plain code block。
- 复制按钮默认复制原始 Markdown text part，不复制 Streamdown 渲染后的 DOM。
- 若使用 AI Elements 本地源码，优先在 message 组件内部把 Markdown renderer 替换为 Streamdown，避免双渲染。

Chat SDK 与 Workflow SDK：

- Chat SDK 不作为 MVP 依赖，只参考 data part / DataStream 思路；artifact、分享、反馈、cloud auth 均不进入 MVP。
- Workflow SDK 不进入 MVP。M4+ 如需定时总结、批量处理或可恢复后台任务，优先采用 SQLite-backed job queue + 主进程定时器/cron；只有用户接受云端 durable execution 时才重新评估 Workflow SDK。

国际化：

- 使用 `i18next` + `react-i18next`。
- 文案目录分 `zh-CN` / `en-US`，默认 `zh-CN`。
- 主进程错误返回稳定 `code`，渲染进程按当前语言映射文案；日志仍使用英文错误码和脱敏上下文。
- lark-cli 原始错误只作为“详细信息”展示，外层用户提示由应用本地化。

主要视图：

- 左侧会话列表：新建、搜索、恢复、删除。
- 中央聊天流：用户消息、assistant 流式消息、工具调用折叠块、错误块。
- 底部输入区：多行输入、发送、停止生成、重新生成。
- 设置面板：硅基流动 API Key、飞书 appId/appSecret、授权状态、语言、主题。

状态管理：

- 轻量 UI 状态可用 React state/context。
- 若聊天流、会话列表、设置状态跨组件复杂，再引入 Zustand；不作为首个必须依赖。

## 10. 打包与发布

沿用 Electron Forge：

- macOS：DMG + ZIP；Apple Developer ID 签名和 notarization 通过现有环境变量配置。
- Windows：Squirrel installer；优先 x64，ARM64 作为后续确认项。
- 自动更新：保留 `electron-updater` + GitHub Releases。
- 内置资源：lark-cli 放入 `packagerConfig.extraResource`，按 `process.platform` 和 `process.arch` 解析。

lark-cli 子资源签名要求：

- macOS：`Contents/Resources/lark-cli/bin/lark-cli` 是独立 Mach-O，可执行文件必须参与 codesign。Forge 签名配置需要通过 `osxSign.optionsForFile` 或等价 hook 对该路径启用 hardened runtime，并复用主 app 的签名身份和必要 entitlements。
- 若 M1 确认 lark-cli 是 V8-based 单体，macOS entitlements 需评估并验证 `com.apple.security.cs.allow-jit`、`com.apple.security.cs.allow-unsigned-executable-memory`，必要时加入 `com.apple.security.cs.disable-library-validation`；若是原生 Go/Rust 编译产物，不默认开启这些宽权限。
- macOS notarization 必须在包含 lark-cli 子资源后执行；签名后不得再写入 app bundle 内文件。
- Windows：`lark-cli.exe`、主 app、Squirrel installer、`Update.exe` 都需要 Authenticode 签名。MVP 可用 OV 证书发布，但要预期 SmartScreen 冷启动拦截；正式推广优先 EV 证书。
- 发布流水线必须校验 lark-cli 二进制 checksum 与 `@larksuite/cli` 包内 `checksums.txt` 匹配，避免打包被篡改资源。

发布前必须验证：

- macOS Apple Silicon、macOS Intel 启动和授权流程。
- Windows 10/11 安装、升级、卸载。
- lark-cli 资源路径在开发、package、make 三种模式下均可解析。
- 公证后在干净 macOS 机器上启动时 Gatekeeper 静默放行。
- 签名后没有在 app bundle 内写入新文件，避免破坏签名。

## 11. 安全策略

MVP 必须实现：

- 不把通用 shell 暴露给模型。
- 写操作二次确认，确认 UI 显示目标、动作、主要内容和风险。
- 工具输入使用 Zod schema 校验。
- 子进程参数数组化，禁用 shell 拼接。
- 所有日志脱敏：API Key、appSecret、authorization code、access token、refresh token 默认替换为 `[REDACTED]`。
- 渲染进程启用现有 `contextIsolation: true`、`nodeIntegration: false`。
- 外部 URL 仅允许 `https://` 和飞书授权域名；其他 URL 不自动打开。
- 打包时校验内置 lark-cli 二进制完整性，运行时发现 checksum 不匹配则拒绝执行并提示重新安装。

MVP 不做：

- 企业级审计日志。
- 多账号隔离。
- 自定义插件权限系统。
- 组织级管理员策略。

## 13. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| Kimi-K2.6 工具调用稳定性不足 | 对话无法可靠完成 S1-S3 | M1 先做真实链路 spike；收紧工具 schema 和 system prompt |
| SiliconFlow 先输出大量 `reasoning_content` | UI 首个可见 token 可能明显晚于请求开始 | AI SDK text stream 已验证可用；M1.0 继续验证 `UIMessageChunk` 映射，并在 UI 显示连接/思考状态，必要时单独保存 reasoning usage |
| Structured Outputs 不可依赖 | 工具参数或结构化响应可能校验失败 | MVP 不依赖 strict structured outputs；本地 Zod / JSON Schema 二次校验，失败时让模型重试或终止 |
| lark-cli 输出 HTML/大段 JSON 直接进入模型 | 上下文膨胀、泄露不必要字段、回答不稳定 | 工具层做字段白名单、HTML 清洗、长度裁剪；完整原始结果只落库，回传模型使用摘要或受控片段 |
| `UIMessageChunk + IpcChatTransport + useChat` 路线不成立 | AI Elements 不能直接接入，UI 状态机返工 | M1.0 先做 A1a/A1b；失败即退回自定义 IPC 事件协议 + 自研 UI 状态机 |
| Streamdown / AI Elements 与 Electron CSP 或 Tailwind 4 不兼容 | 聊天 UI 组件需要降级 | 渲染层作为体验项处理；AI Elements 退源码参考，Streamdown 退 plain code block |
| lark-cli 授权流程跨平台差异 | 用户无法完成授权 | 授权流程独立封装，开发期覆盖 macOS/Windows |
| `@larksuite/cli` 版本或输出协议变化 | 授权解析和工具调用被上游破坏 | 锁定版本；升级前跑授权、文档、消息全量回归 |
| lark-cli 打包体积或资源路径复杂 | 安装包变大或运行失败 | M1 第 1 周确认 `@larksuite/cli` 资源复制、checksum 和运行路径 |
| lark-cli 子二进制签名失败 | macOS 公证失败或 Windows 安装拦截 | M3 前把子二进制纳入 codesign / signtool 验证 |
| lark-cli 在 hardened runtime 下无法启动 | macOS 签名包运行失败 | M1 spike 内确认二进制类型并验证签名后启动 |
| safeStorage 不可用 | 无法保存凭证 | 正式版阻止保存并提示，不明文降级 |
| 写操作误执行 | 误发消息或误创建文档 | 写操作二次确认，默认展示可审计摘要 |
| Windows stdout 编码异常 | 工具结果乱码 | 强制 UTF-8 环境变量，必要时按平台转码 |
| 首 token 超 3 秒 | 体感变慢 | UI 先展示连接和工具状态；实际 token 延迟埋点记录 |
